# ProofGraph 상세 로드맵

> 최초 작성: 2026-11-16 · 브리핑은 [../PROJECT.md](../PROJECT.md) · 진행 상황은 [STATUS.md](STATUS.md)
> Claude는 세션마다 **현재 단계 섹션만** 읽는다. 체크박스는 작업이 끝날 때마다 갱신한다.

## 읽는 법

각 단계는 같은 구조로 되어 있다.

- **목표 / 예상 기간:** 기간은 주 20시간 투입을 가정한 값이다. 실제 투입 시간은 `P0-C2`에서 확인하고 다시 조정한다.
- **작업:** 체크리스트. **[직접]**은 사용자가 먼저 작성하는 작업이다 (CLAUDE.md의 학습 프로토콜).
- **공부할 것:** 그 단계를 진행하려면 알아야 하는 개념. "왜"와 "어디까지"를 함께 적었다.
- **산출물·증빙:** 외부에 보여 줄 수 있는 결과물.
- **완료 기준:** 이것을 모두 채워야 다음 단계로 간다.
- **Claude 질문:** 착수할 때, 진행 중 특정 상황에서, 검수할 때 Claude가 사용자에게 물어야 하는 질문.
  - 유형: **D** 결정, **C** 확인, **L** 학습 점검, **E** 외부 평가(채용 담당자·면접관의 시선), **R** 회고
  - 답은 [QUESTIONS.md](QUESTIONS.md)에 기록한다. 여기 없는 질문도 필요하면 언제든 묻는다.

## 목표 직무에 따른 조정 (P0-D1: AI 엔지니어, P0-C2: 주 30시간 이상)

- **기간:** 아래 각 단계의 예상 기간은 주 20시간, 기초 지식이 있는 경우를 기준으로 했다. 주 30시간이지만 숙련도가 전 언어 0(P0-C3)이라 **기간은 표기대로** 본다 (전체 약 6개월). 1단계가 끝나면 실제 속도로 다시 계산한다.
- **언어 입문 과제:** 어떤 언어든 처음 쓰기 전에 그 단계 첫 작업으로 **입문 과제(0.5~1주)**를 한다. 작은 CLI 프로그램 하나를 직접 만들고, `tutor` 에이전트의 퀴즈를 통과한 뒤 본 작업에 들어간다.
  - Java: 1단계 시작 전 (부트캠프 경험이 있으니 복습 속도를 보고 숙련도를 다시 평가한다)
  - Python: 1.7 전 · TypeScript: 1.11 전 · Go: 4.1 전 · Rust: 6.1 전
  - SQL: 1.1과 함께 (ERD를 실제 테이블과 쿼리로 확인)
- **[직접] 작업의 강도:** 숙련도 0~1인 동안에는 Claude가 먼저 짧은 예제로 개념을 보여 주고, 사용자는 그 예제를 변형해서 [직접] 작업을 한다. 숙련도 2 이상이 되면 예제 없이 사용자가 먼저 작성한다.
- **3단계가 핵심 단계다.** 검색, RAG 평가, LLM 보안을 가장 깊게 하고, 면접 소재의 중심으로 삼는다.
- **LLM이 들어가는 모든 기능에 평가를 붙인다.** 1.9(기술 추출)와 2.5(근거 기반 생성)도 작은 평가 세트와 수치를 남긴다.
- **Python 비중을 키운다.** ai-pipeline과 MCP 서버(Python)에서 비동기, 타입, 테스트를 깊게 다룬다.
- **6단계 후보에 추가:** 에이전트 평가(도구 사용 정확도), 로컬 임베딩·재정렬 모델 비교, LLM 비용·지연 최적화(캐싱, 배치).

## 전 단계 공통 트랙

매 단계 진행하면서 계속하는 것.

- [ ] **학습 로그:** 작업이 끝날 때마다 `docs/learning-log/YYYY-MM-DD-주제.md`
- [ ] **ADR:** 되돌리기 어려운 결정마다 `docs/adr/NNNN-제목.md`
- [ ] **면접 회고 입력:** 실제 면접을 보면 받은 질문을 기록한다 (2단계부터는 시스템에 입력)
- [ ] **단계 회고:** 단계가 끝날 때 R 유형 질문으로 회고하고, 로드맵을 조정한다

**단계 종료 공통 질문 (모든 단계)**
- `R1` 이번 단계에서 가장 어려웠던 것과, 그걸 면접에서 어떻게 설명할 것인가?
- `R2` 계획보다 오래 걸린 작업은? 원인은 기술 부족인가, 범위 과다인가?
- `R3` 로드맵에서 빼거나, 순서를 바꾸거나, 추가할 것은?
- `E1` 지금 상태의 GitHub와 공개 페이지를 처음 보는 면접관은 무엇을 질문할까? 그 질문에 답할 수 있는가?

- 추출 결과 품질이 낮으면: 프롬프트를 고칠지, 기준을 바꿀지, 사람 검토를 늘릴지
- 엔티티를 추가하거나 관계를 바꾸고 싶어지면: 스키마 변경 전에 반드시 묻는다
- `P1-D5` 첫 배포 방식: 단일 VM / PaaS / 정적 호스팅 + API 서버 분리

**검수할 때**
- `P1-L1` 영속성 컨텍스트와 N+1 문제를 이 프로젝트 코드로 설명해 보라
- `P1-L2` 트랜잭션 경계를 왜 서비스 계층에 두었는가?
- `P1-L3` 공개 프로필을 왜 정적 생성으로 만들었는가? 대안과 비교하면?
- `P1-E2` 현직 개발자 1명에게 공개 프로필을 보여 줄 수 있는가? 받은 피드백은?
- `P1-E3` 공개 프로필에서 과장되어 보이는 주장이 있는가? 근거가 약한 기술은?

## 2단계 — 공고 적합도

**목표:** 채용공고를 원클릭으로 저장하고, 내 그래프와 대조해 적합도, 갭, 맞춤 이력서 초안을 만든다. **실제 지원에 바로 쓰기 시작한다.**
**예상 기간:** 4주

### 작업
- [ ] **2.1 크롬 확장 (MV3):** 보고 있는 공고 페이지를 원클릭으로 저장 (본문, URL, 회사명)
- [ ] **2.2 공고 파싱:** LLM으로 필수·우대 기술, 경력 조건, 직무를 구조화. Company, JobPosting, Role 엔티티
- [ ] **2.3 [직접] 적합도 점수 알고리즘:** 설명 가능한 점수 (무엇 때문에 몇 점인지 보여야 한다)
- [ ] **2.4 갭 리포트:** 부족한 기술, 근거가 약한 기술, 학습 추천
- [ ] **2.5 맞춤 문서 초안:** 공고별 이력서 요약과 자소서 초안. **모든 문장에 내 증빙 링크.** 증빙 없는 주장은 생성하지 않는다
- [ ] **2.6 예상 면접 질문:** 공고와 내 프로젝트를 근거로 생성
- [ ] **2.7 [직접] 지원 현황 관리:** 상태 흐름 (관심 → 지원 → 서류 결과 → 면접 → 결과). 실제 결과가 쌓여 점수 검증에 쓰인다
- [ ] **2.8 면접 회고 입력:** 받은 질문과 답변 자체 평가를 기록해 그래프에 연결

### 공부할 것
| 주제 | 왜 | 어디까지 |
|---|---|---|
| 브라우저 확장 구조 | 원클릭 수집 | MV3, content script와 service worker, 권한 최소화, 인증 토큰 보관 |
| 점수화와 설명 가능성 | 적합도 | 가중합, 정규화, 점수 근거 표시 |
| 근거 기반 생성 | 이력서 초안 | 출처 강제, 환각 검출, 생성 결과 검증 |
| 상태 기계 | 지원 현황 | 상태와 전이, 잘못된 전이 막기 |
| SQL 집계 | 갭 분석 | GROUP BY, 서브쿼리, 집합 연산 |

### 산출물·증빙
- 크롬 확장, 실제 지원에 사용한 공고별 갭 리포트
- 적합도 알고리즘 설명 문서 (ADR)

### 완료 기준
- 공고 저장부터 갭 리포트와 맞춤 초안까지 **5분 이하**
- 실제 공고 10개 이상을 저장하고 분석했다
- 생성된 초안의 모든 주장에 증빙 링크가 있다

### Claude 질문
**착수할 때**
- `P2-D1` 적합도에서 필수와 우대 기술의 가중치, 경력 조건 미충족을 어떻게 처리할까?
- `P2-D2` 자소서와 이력서 초안의 톤과 분량은?
- `P2-D3` 지원 현황의 상태 단계 정의
- `P2-C1` 저장할 공고의 범위: 본문 전체 저장이 해당 사이트 약관상 괜찮은가? (사용자가 확인)
- `P2-C2` 지금 관심 있는 회사와 공고 3~5개는? (첫 테스트 데이터)

**진행 중 (상황이 생기면)**
- 점수가 직관과 크게 다르면: 사용자의 직관과 알고리즘 중 무엇을 고칠지 묻는다
- 증빙이 부족해 초안이 빈약하면: 어떤 프로젝트나 경험이 빠졌는지 묻는다

**검수할 때**
- `P2-L1` content script와 service worker의 권한 차이는?
- `P2-E1` 생성된 자소서를 실제로 제출할 수 있는 수준인가? 무엇을 고쳤는가?
- `P2-E2` 적합도 점수 높음과 실제 서류 결과가 일치하는가? (결과가 쌓이면)

## 3단계 — 검색, RAG, 공개 챗봇

**목표:** 내 모든 데이터에 대해 출처가 달린 질의응답을 만들고, **품질을 숫자로 측정**하며, 공개 챗봇이 비공개 데이터를 절대 꺼내지 못하게 한다. 면접에서 가장 깊게 파고들 단계다.
**예상 기간:** 5주

### 작업
- [ ] **3.1 청킹 전략:** 문서 유형별 분할 기준 (코드, 노트, 공고)
- [ ] **3.2 임베딩 파이프라인:** 모델 선택, 배치 처리, 재임베딩 전략
- [ ] **3.3 벡터 검색:** pgvector 인덱스 (HNSW), 필터 결합
- [ ] **3.4 키워드 검색:** Postgres 전문 검색으로 시작 (Rust 엔진은 6단계)
- [ ] **3.5 [직접] 하이브리드 검색:** 키워드와 벡터 결과 결합 (예: RRF), 재정렬
- [ ] **3.6 답변 생성:** 출처 인용 필수, 근거 없으면 "모른다"
- [ ] **3.7 [직접] 평가 세트 구축:** 질문 50~100개와 정답 문서. `eval/`에 저장
- [ ] **3.8 평가 도구:** recall@k, MRR, 답변 충실도(LLM 판정). **CI에서 기준 미달 시 실패**
- [ ] **3.9 검색 단계 접근 제어:** 모든 문서에 공개 범위 필드. 공개 챗봇의 조회는 공개 범위로 필터링된 상태에서만 실행
- [ ] **3.10 프롬프트 인젝션 방어:** 수집 콘텐츠 격리, 지시문 무시 처리, 출력 검증
- [ ] **3.11 [직접] 레드팀 세트:** 비공개 데이터를 빼내려는 질문 50개. 노출 0건이 CI 기준
- [ ] **3.12 요청 제한:** 공개 챗봇에 IP·링크별 속도 제한
- [ ] **3.13 공개 챗봇 UI:** "저에 대해 물어보세요"

### 공부할 것
| 주제 | 왜 | 어디까지 |
|---|---|---|
| 정보 검색 기초 | 검색 품질의 원리 | 역색인, TF-IDF, BM25 |
| 임베딩과 벡터 검색 | 의미 검색 | 임베딩의 의미, 코사인 유사도, 근사 최근접 탐색(HNSW)의 원리와 트레이드오프 |
| 하이브리드 검색과 재정렬 | 품질 향상 | RRF, cross-encoder 재정렬 |
| RAG 평가 | 품질을 숫자로 | recall@k, MRR, 충실도, LLM 판정의 한계 |
| LLM 보안 | 공개 챗봇 | OWASP LLM Top 10, 간접 프롬프트 인젝션, 데이터 유출 |
| 요청 제한 알고리즘 | 남용 방지 | 토큰 버킷, 슬라이딩 윈도우, Redis 구현 |

### 산출물·증빙
- 평가 리포트 (개선 전후 수치), 레드팀 결과
- "검색 단계 접근 제어" 설계 ADR — 면접 핵심 소재

### 완료 기준
- recall@5 ≥ 0.8 (또는 `P3-D2`에서 정한 기준)
- 레드팀 50개 노출 0건, CI에서 자동 검증
- 공개 챗봇의 모든 답에 출처가 있다

### Claude 질문
**착수할 때**
- `P3-C1` 외부인이 물을 법한 질문 20개를 직접 써 줄 수 있는가? (평가 세트의 씨앗, 사용자만 쓸 수 있다)
- `P3-D1` 공개 챗봇이 대답하면 안 되는 주제는? (연봉, 개인 연락처, 다른 회사 지원 현황 등)
- `P3-D2` 품질 기준선: recall@5 목표치와, 미달 시 배포를 막을 것인가?
- `P3-D3` 임베딩 모델 선택 기준: 비용, 한국어 성능, 로컬 실행 여부

**진행 중 (상황이 생기면)**
- 평가 점수가 기준에 못 미치면: 청킹, 검색, 생성 중 어디를 먼저 개선할지 수치를 보여 주고 묻는다
- 레드팀에서 노출이 발견되면: 즉시 보고하고, 원인과 수정 방향을 묻는다

**검수할 때**
- `P3-L1` 프롬프트로 막는 것과 검색 단계에서 막는 것의 차이는? 왜 후자인가?
- `P3-L2` HNSW 인덱스의 정확도와 속도 트레이드오프를 설명하라
- `P3-E1` 면접관이 "RAG 품질을 어떻게 보장했나요?"라고 물으면 어떻게 답할 것인가?
- `P3-E2` 지인에게 공개 챗봇을 깨 보라고 부탁할 수 있는가? 결과는?

## 4단계 — 인텔리전스 피드

**목표:** 테크 뉴스, AI 활용법, 직군 동향을 수집해 **내 그래프와의 관련도로 걸러 낸** 주간 브리핑을 만든다. 공고 데이터로 기술 수요 트렌드를 본다.
**예상 기간:** 4주

### 작업
- [ ] **4.1 collector 서비스 (Go):** RSS, Hacker News API, GeekNews 등 동시 수집. 요청 속도 제한, 재시도, robots.txt 준수
- [ ] **4.2 메시지 큐:** Redis Streams로 수집 → 처리 파이프라인 연결
- [ ] **4.3 중복 제거:** 같은 소식의 여러 기사 묶기 (SimHash 등)
- [ ] **4.4 요약과 관련도:** 요약 생성(전문 저장 안 함), 내 기술·목표 직무와의 관련도 점수
- [ ] **4.5 [직접] 트렌드 분석:** 공고에서 기술별 언급 빈도 시계열. SQL 윈도우 함수
- [ ] **4.6 주간 브리핑:** 일정 실행으로 생성. 관련 뉴스, 트렌드 변화, 새 공고, 내 갭과의 연결
- [ ] **4.7 [직접] 복습 퀴즈:** 내 노트로 문제 생성, 간격 반복 알고리즘(SM-2)
- [ ] **4.8 작업 관리:** Prefect 또는 Temporal로 파이프라인 재시도와 모니터링
- [ ] **4.9 (선택) 공개 트렌드 리포트:** "이번 달 신입 공고 기술스택 트렌드" 공개 페이지

### 공부할 것
| 주제 | 왜 | 어디까지 |
|---|---|---|
| Go 기초 | collector | 문법, 인터페이스, 에러 처리 관례, 모듈 |
| Go 동시성 | 다수 출처 동시 수집 | goroutine, channel, context로 취소, worker pool, errgroup |
| 메시지 큐 | 서비스 간 비동기 | at-least-once, 소비자 그룹, 재처리, 멱등성 |
| 작업 관리(워크플로) | 파이프라인 신뢰성 | 재시도, 백오프, 실패 처리 |
| SQL 고급 | 트렌드 | 윈도우 함수, 시계열 집계, 실행 계획(EXPLAIN) |
| 간격 반복 학습 | 복습 퀴즈 | SM-2 알고리즘 |

### 산출물·증빙
- Go 서비스, 주간 브리핑 실물, 트렌드 차트
- 동시성 설계 ADR

### 완료 기준
- 매주 브리핑이 자동 생성된다
- 수집이 실패해도 재시도되고, 같은 기사가 중복 저장되지 않는다
- 트렌드 쿼리의 실행 계획을 분석하고 인덱스로 개선한 기록이 있다

### Claude 질문
**착수할 때**
- `P4-C1` 구독할 소스 목록 (뉴스, 기술 블로그, AI 활용법 출처)
- `P4-D1` 브리핑 주기와 받는 방법 (웹 페이지 / 이메일 / 알림)
- `P4-D2` 관심 직군 키워드와 트렌드에서 추적할 기술 목록
- `P4-D3` 공개 트렌드 리포트를 할 것인가?

**진행 중 (상황이 생기면)**
- 소스의 약관이나 robots.txt가 수집을 금지하면: 대안을 제시하고 묻는다
- 브리핑이 너무 길거나 관련 없는 내용이 많으면: 걸러 내는 기준을 묻는다

**검수할 때**
- `P4-L1` context 취소가 goroutine 누수를 어떻게 막는가?
- `P4-L2` at-least-once 전달에서 중복 처리를 어떻게 막았는가?
- `P4-R1` 브리핑을 실제로 매주 읽고 있는가? 읽지 않는다면 왜인가?

## 5단계 — 공유, 통합, 운영

**목표:** 회사별 공유 링크와 맞춤 페이지, MCP 서버를 완성하고, 클라우드에서 **측정 가능한 운영 체계**로 돌린다.
**예상 기간:** 4주

### 작업
- [ ] **5.1 [직접] 공유 링크:** 서명된 토큰, 공개 범위, 만료, 취소
- [ ] **5.2 회사 맞춤 페이지:** 링크에 연결된 공고의 요구 기술 증빙을 먼저 보여 준다
- [ ] **5.3 조회 통계:** 링크 열람 여부와 섹션별 조회수만 집계 (개인 식별 안 함)
- [ ] **5.4 MCP 서버:** 내 그래프 조회, 공고 분석, 갭 조회를 도구로 공개. Claude Code에서 사용
- [ ] **5.5 "AI와 일하는 방식" 페이지:** Claude Code로 무엇을 자동화했고 어떻게 검증했는지
- [ ] **5.6 IaC:** Terraform으로 클라우드 인프라 정의
- [ ] **5.7 배포 파이프라인:** main 병합 시 자동 배포, 롤백 방법
- [ ] **5.8 관측성:** OpenTelemetry로 요청과 LLM 호출 전 구간 추적, Grafana 대시보드
- [ ] **5.9 LLM 비용 대시보드:** 기능별 비용, 상한 초과 경보
- [ ] **5.10 [직접] 부하 테스트:** k6로 공개 페이지와 챗봇 부하, 병목 분석과 개선 전후 수치
- [ ] **5.11 백업과 복구 훈련:** 실제로 복구해 보고 걸린 시간 기록
- [ ] **5.12 보안 점검:** 의존성 취약점, 비밀값 노출, 권한 검토
